### ✅ the flagship contract IS snapped — BOTH journeys, and how

`reviewRoundTrip.acceptance.test.ts` carries one mask, `asMaskedStdout`, and two journeys through
it. **one mask serves both on purpose** — two masks would drift apart, and a drifted mask is a
snapshot that guards no one.

| journey | what it drives | what it snaps |
|---|---|---|
| `[case1]` success | a real `rhx review --brain anthropic/claude/sonnet/v5` against a real rubric and target | the masked LIVE stdout — the whole verdict tree a caller reads |
| `[case2]` failure | the same CLI handed `--brain anthropic/claude/bogus/v9` | the masked stderr — the whole failure a caller reads |

that is the mask-then-snap-live method `rule.require.contract-snapshot-exhaustiveness` prescribes
for a non-deterministic output.

**what the mask covers.** `[case1]` per-run spans: the temp output dir, the log stamp dir, the
spinner, the owl verdict line, the summary tail leaf, the price, the duration, the percentages,
and each count. `[case2]` crash-dump spans: ansi codes, the pnpm content-hash path, the
`file.js:line:col` throw site, the echoed source line, the stack, and the node runtime version.
the `[case2]` masks are **provable no-ops on `[case1]`** — its snapshot is byte-identical before
and after they were added.

**cost.** `[case1]` rides the same live call the numeric-count probes already read, so it costs no
extra model spend. `[case2]` costs **no credential and no model spend at all** — an undeclared
brain is refused at discovery, before any client is constructed.

**what stays masked, on purpose:** the verdict prose and the counts. a snapshot that froze
`0 blockers` would redden the moment a model read the fixture differently, and a flaky clamp gets
muted and then guards no one.

⚠️ **two facts a READ of the generated snapshots surfaced, which reason had not.**

1. the `[case1]` spinner repaints with a **carriage return**, so its frames are `\r`-separated. a
   collapse written against `\n` matched none of them — a defect visible only as a frame count
   that moved 37 → 44 across two GREEN runs, since jest renders a lone `\r` as a line break.
2. a failed `rhx review` escapes as an **uncaught node throw**, not a rendered error. its stderr
   carries five environment-dependent spans, every one of which moves on a dep bump or a runtime
   upgrade. the first `[case2]` capture would have flaked on the next `npm update`.

both were caught because the snapshots were opened rather than trusted.

**and `[case2]` clamps more than the failure.** the error's metadata payload lists every
discoverable slug, so that snapshot also proves **all 17 atom and 18 repl slugs reach discovery** —
which is the wish's "expose for opt-in" criterion, held as a side effect of the failure journey.

### i035 — the one this gate caught

`genBrainRepl` omitted `settingSources`. the sdk documents that omission at `sdk.d.ts:2046-2056`:

> *"When omitted, all sources are loaded (matches CLI defaults). Pass `[]` to disable filesystem
> settings (SDK isolation mode)."*

so every `.ask()` / `.act()` silently loaded `~/.claude/settings.json`, the caller's project
`.claude/settings.json`, `.claude/settings.local.json`, and `CLAUDE.md`. **those sources carry
hooks.**

**how it surfaced.** `genBrainRepl.integration.test.ts` `[case2]` asked haiku to *"respond with
exactly: hello from claude code"*. it returned a markdown status report about **this repo's route
stone** — our own `SessionStart` hook output, injected into the agent's context, where it
outranked the caller's prompt.

**why it is a consumer defect, not a test defect.** a package whose `.ask()` absorbs whatever
`.claude/` sits in the caller's cwd gives two different answers to one call on two machines, and
runs hook commands the library author never declared. that is `rule.forbid.unexpected-defaults`
and the opposite of `rule.require.pitofsuccess`.

**the fix, at cause.** the inline options object was extracted to a named transformer,
`repls/asQueryOptions.ts`, which passes `settingSources: []`. the extraction is the point: the sdk
`query` sits behind a credential guard, so an inline object could be proven only by a live agent
run — which is exactly how this shipped unnoticed. as a pure transformer it is clamped with no
credential, no network, no charge (`rule.require.named-transformers`).

`[]` rather than `['project']` because `role.briefs` is this contract's one declared context
channel; to also load `CLAUDE.md` would hand the agent a second channel the caller never opted
into and cannot see.

**the dogfood.** with `settingSources` removed, the clamp goes red 4 ways (2 assertions × 2 modes)
and prints `Expected: []` / `Received: undefined` — precisely the two states that look alike in a
diff and behave like opposites. restored → green. the live `[case2]` that exposed it now passes.

**twin check** (`repair both twins in the same pass`): the atom has **no analogous surface** — it
is a plain HTTPS call to the Messages API with no subprocess and no config load. the asymmetry is
by design, not an unrepaired twin.

**the meta-lesson, and it is the second instance in this behavior.** i033 was hidden by a red
suite; i035 was hidden by a stale claim of green. both are the same shape: *a claim of coverage
that was never re-verified*. the cure in both cases was to run the check.

4. 🔴 **a workflow that fails at parse time emits NO check, so its absence reads as a pass — and
   that hid a six-week outage.** the break is repaired; **the gap that concealed it is not**, and
   only the human can close it, since the fix is a branch protection setting.

   **the visibility gap — and ⚠️ i first diagnosed its CAUSE wrong.**

   the observation was right: `gh pr checks 33` listed four checks with no `test` among them, and
   `check-suites/<id>/check-runs` returned **empty**. so `rhx git.release` reported *"all checks
   passed"* while the entire suite never ran — a green that means far less than it looks, on the
   exact gate a release rides.

   the cause i inferred was wrong. i wrote that `test.yml` triggers on `push` rather than
   `pull_request`, *"so its run never becomes a check run on the PR"*. **that is false, and this
   behavior's own run disproves it:** the commit that restored the `permissions:` block surfaced
   all 8 `suite / *` jobs in `gh pr checks`, with the trigger **unchanged** — still `push`, still
   no `pull_request`. push-triggered jobs attach to the head sha and do show on the PR.

   the real cause is narrower and sharper: **a run that fails at PARSE time emits no check runs at
   all.** so a `startup_failure` does not render as a red check — it renders as no check, and a
   broken workflow becomes indistinguishable from a workflow that was never configured.

   ⚠️ the error was to infer a cause from a correlation (`test` is push-triggered AND absent from
   the PR) instead of testing it. the fix for the stated cause would have been to add a
   `pull_request` trigger — which would have changed a thing that was never broken, and left the
   actual hazard fully intact.

   **the break — FOUND and FIXED.** it was **not caused by this behavior**:
   `git show --stat <feat-commit> -- .github/` is empty, so the feature commit touched no workflow.

   ⚠️ **the timeline, corrected — i first overstated it.** i wrote that `test` was
   `startup_failure` "on every run since 2026-07-28". `gh run list --workflow test.yml` says
   otherwise: it last ran **green** on 2026-07-28 (the v0.4.3 release), then **no push touched it
   for six weeks**, and the first push after that window (2026-09-05) hit `startup_failure`. so
   it did not fail repeatedly and unnoticed — the default permission tightened inside a quiet
   window, and the break surfaced on the very next run. that is less dire than i framed it, and a
   sharper hazard: **a rarely-fired workflow can be broken by an environment change it never
   saw**, and it will not tell you until you need it.

   the cause was an absent `permissions:` block on `test.yml`. `.test.yml` declares
   `permissions: id-token: write` for its aws oidc step, and a caller may only grant a permission
   it holds itself — so a caller that omits the block hands down the default, and once that
   default tightened to read-only the call became unsatisfiable. github rejects that at PARSE
   time, which is why it yielded a 0s `startup_failure` with no job, no annotation, and no error
   text reachable through the api. peer repos on this template carry the block; this one had lost
   it.

   ⚠️ **one wrong hypothesis was committed before the right one.** an earlier `cont(cicd)` claimed
   `on: workflow_call:` plus a bare `secrets.*` read was invalid and removed the trigger. that is
   false — `ehmpathy/rhachet-brains-fireworksai` declares both, so the pattern is the template
   norm. it was reverted, and the false claim was corrected in the next commit message rather than
   left to stand in the log.

   **what the first green run then exposed.** with `test` alive for the first time in six weeks,
   `test-acceptance-locally` went red on a gap no one could have seen while the suite never ran:
   `rhx review` is a skill of `repo=bhrain/role=reviewer`, and that role is linked by
   `package.json`'s `prepare`, which is guarded by `[ -z $CI ]` and so is skipped in ci. the new
   `reviewRoundTrip` acceptance test therefore passed on every dev machine and failed in ci with
   `no skill "review" found in any linked role`.

   fixed by a `pretest:acceptance:locally` → `prepare:roles:reviewer` npm pre-hook that links the
   one role the suite needs. proven red→green **with a control**: the reviewer link was removed to
   reproduce ci's exact error, then the suite was run from that same absent state and the hook
   relinked it for 37/37 green. why `package.json` over `.test.yml`, and why `roles link` over
   `init --roles`, is recorded in the test's own header.

   ⚠️ **do not read a green `rhx git.release` as a green suite until the gap is closed.**

   the durable repair is **not** a `pull_request` trigger — that was the fix for the cause i got
   wrong, and it would change a thing that works. it is to mark the `suite / *` jobs as **required
   status checks** on the branch protection rule. a required check that never reports **blocks**
   the merge, which is the one protection that bites on a `startup_failure`, since the failure
   mode is an absent check rather than a red one.

   until then, absence reads as consent: a suite that never ran and a suite that passed are the
   same green from the PR — which is precisely how the break and a ci-only test gap both stayed
   hidden. only the human can set branch protection, so this stays a council item.

   **🔴 the same defect was latent in `publish.yml`, and it would have failed the prod release.**
   found by a declapract conformance sweep, not by CI — because `publish.yml` fires only on a
   `v*` tag, so CI had no occasion to reveal it.

   it calls two workflows that each declare `permissions: id-token: write` — `.test.yml` (aws
   oidc) and `.publish-npm.yml` (npm provenance) — and granted neither. same shape, same cause,
   same silent parse-time rejection. it last ran green on 2026-07-28, before the tightening, and
   had not run since, so the next release would have been the first to discover it.

   the prediction rests on a controlled experiment rather than a resemblance: `test.yml` calls the
   **same** `.test.yml`, and to restore that block — and only that block — took it from
   `startup_failure` to green. `ehmpathy/rhachet-brains-fireworksai` carries the block on its
   `publish.yml`; this repo had lost it. fixed here.

   a sweep of every `uses: ./.github/workflows/` caller confirms the class is now closed:
   `.declastruct.yml` and `.install.yml` declare no permissions, so `provision.yml` needs none —
   and provision passes live today.

5. 🟠 **`declapract apply` would regress cicd — do NOT run it.** the conformance check the human
   asked for was run (`npx declapract plan --practice cicd-common`, `--practice cicd-package`).
   six files report `FIX_AUTOMATIC`, and **every diff is a deliberate local hardening that
   `declapract-typescript-ehmpathy@0.47.16` does not yet model.** to apply would break CI twice
   over:

   | deviation | what apply would do | consequence |
   |---|---|---|
   | 45 action refs pinned to full SHAs | revert to `@v4` tags | ⛔ every workflow blocked by org policy |
   | `permissions:` on `test.yml` / `publish.yml` | delete it | ⛔ parse-time `startup_failure` returns |
   | `secrets: openai-api-key` plumbing | delete it | live tests lose `ANTHROPIC_API_KEY` |
   | `build` step before `test:types` | delete it | types run without `dist/` |
   | `npm@11` pin in `.publish-npm.yml` | revert to `@latest` | ⛔ npm@12 EBADENGINE (fixed in v0.4.3) |

   ⚠️ the SHA-pin row is not a preference. the org rejects tag refs outright, in its own words:
   *"The actions actions/checkout@v4, … are not allowed in ehmpathy/rhachet-brains-anthropic
   because all actions must be pinned to a full-length commit SHA."* the template still ships
   `@v4`, so **the template is behind the policy it is meant to encode.**

   ⚠️ and the template is internally inconsistent on the very defect above: its `.test.yml`
   declares `permissions: id-token: write` while its `test.yml` grants none. so a repo stamped
   from it today inherits the outage. that is upstream's to fix, not this repo's — but it is why
   "conform to declapract" and "keep CI green" are, right now, in genuine conflict.

   **the verdict: the repo conforms in structure; the residual diffs are the template's debt, not
   this repo's drift.** the durable repair is to land the SHA pins and the caller `permissions:`
   blocks in `declapract-typescript-ehmpathy` itself, so the whole fleet gets them. that is a
   council item — it is a change to another repo.

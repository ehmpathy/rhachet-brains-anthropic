## 🔴 the defect found by accident, which is bigger than the one we came for

while i checked whether the acceptance snapshot had caught the 3→17 slug change, i noticed
it had **silently absorbed** it. it should have gone red.

root cause, in `package.json`:

```
$([ -n $RESNAP ] && echo '--updateSnapshot')
```

`$RESNAP` is unquoted. when unset it expands to an empty word, so the test becomes `[ -n ]`
— a **single-argument** test, which asks whether the string `"-n"` is non-empty. it always
is. so `--updateSnapshot` was passed on **every run**, and **every snapshot in this repo has
been auto-rewritten rather than checked**.

i verified this rather than reasoned it: i injected a bogus slug into the snapshot, ran
acceptance, and it **passed** — then the file was silently rewritten back.

**why this matters beyond a typo:** `rule.require.snapshots` says snapshots exist so
reviewers can vibecheck an artifact and so drift surfaces in a PR. an always-on
`--updateSnapshot` inverts that: the snapshot records whatever the code just did, so it can
never disagree with it. it is a `rule.forbid.failhide` at the tooling level — a green check
that verifies zero.

it is also, plausibly, part of how `0.4.3` shipped three broken slugs without a murmur.

### fixed, and proven to bite

quoted the variables in all four test scripts. then re-ran the same probe:

| probe | before fix | after fix |
|---|---|---|
| bogus slug in the snapshot | 🎉 passed, file silently rewritten | ✋ **failed** |
| probe reverted | — | 🎉 passed |

⚠️ **flagged for the council, since it leaves the wish's scope.** the fix is one line in a
file i had already touched, the whole suite is green under it, and to leave it would mean
shipping a snapshot i had just watched fail to verify anything. but it repairs a repo-wide
test guarantee that this behavior did not set out to touch, so it deserves a human's eye —
and it is a clean rework, since a revert is one line.

## what execution found that the vision did not

### 1. opus 4 is Google Cloud only, not Bedrock

the vision said the three retired rungs are "retired except on Bedrock and Google Cloud",
taken from the price page's shared note. the per-model deprecation page is narrower for opus
4 specifically: **Google Cloud only**. haiku 3.5 and sonnet 4 do keep both.

this matters because `deprecated.reason` is the only place a caller learns which injected
client still reaches the rung. a reason that named Bedrock for opus 4 would send a Bedrock
caller to a rung that fails there too — the exact silent-failure shape F3 exists to end.
each of the three now carries its own verified platform list rather than a shared one.

### 2. `temperature` / `top_p` / `top_k` return 400 on opus 4.7+

turned up in the spec verification. grepped `src/` — no matches, so we pass none of them and
the hazard is clear today. worth the note because the next contributor who adds one of those
knobs will hit it on the newest rungs only, which is the worst shape of bug to find.

### 3. `effort` has grown past the three levels #490 assumed

the dispatched issue proposes `'low' | 'medium' | 'high'`. the upgraded sdk types it:

```ts
effort?: 'low' | 'medium' | 'high' | 'xhigh' | 'max' | null;
```

so a three-level union would be lossy on arrival. combined with the verified finding that
sonnet 4.5 and haiku 4.5 **reject the parameter outright**, the generic contract needs both
a wider union and a way to express "unsupported". worth relayed to #490 before its shape
sets.

### 4. `useThen` cannot stand in for a primitive

`useThen` returns a proxy, so `expect(proxy).toContain(...)` fails with *"received is not
iterable"*, and a proxy handed to a function that calls `.indexOf` fails likewise. it works
for property access on an object result, not for a string or number. cost me two red runs;
noted here so the next person spends none.

### 5. the registration list, made structural

the vision found (I3) that rhachet discovers only what `getBrainAtomsByAnthropic()`
*returns*, so a slug in the union but absent from that array is invisible to
`rhx review --brain`. it named a hard requirement: register every rung.

execution went one step further and removed the second list entirely. the slug array is now
the single source for the type, the registration, and the generated table. `index.test.ts`
asserts the exact ladder rather than a count — so a gap goes red instead of unnoticed.

⚠️ the trade: a reader who greps `AnthropicBrainAtomSlug =` now finds a derivation rather
than a list. the array sits directly above it with the same comments, so the cost is small,
but it is a real change in where a reader looks.

### 6. the readme table dropped its description column

the generated table carries slug, model, rate, context, thought, cutoff, and deprecated. the
old hand-kept table had a description instead of the middle four. descriptions largely
restate the slug, and the thought column is what prevents a caller from a pin on the
expensive rung by mistake — but the removal is a deliberate change, not an oversight.

⚠️ note the clamp's bound, found while its teeth were tested: a change to `description`
does **not** turn the readme clamp red, because the column is no longer rendered. the clamp
guards what the table shows, which is correct — but it is narrower than "the config
changed", and that is worth stated plainly rather than discovered later.

## ✅ RESOLVED — the `act` flake was an ambiguous PROMPT, not the sdk bump

the r5 measurement stood at **2 failures in 5 samples**, with the agent-sdk bump named as the one
un-ruled-out variable, and i had deferred the isolation experiment on the grounds that a reversal of
council decision F8 is the wisher's call.

⚠️ **that deferral was wrong, and the reviewer who said so was right.** to *run* an experiment and
to *reverse a decision* are two different acts. the experiment is a two-line pin, fully reversible,
and it converts a suspicion into a fact — no wisher input required. only a choice to KEEP the
downgrade would have been F8's to revisit. i conflated the two and stalled a diagnosis behind a
permission i never needed.

### the experiment, run

| arm | agent-sdk | samples | failures |
|---|---|---|---|
| B | `0.1.76` (pinned back) | 8 | 0 |
| A | `0.3.251` (this behavior's bump) | 8 | 1 |

so the bump is **not exonerated** — but 1-in-8 sits far off the 2-in-5 that the deferral was priced
against, and the 8th sample handed over the evidence that actually mattered: a **second** distinct
failure string.

```
sample 1 (r5):  "structured output tool invoked as requested."
sample 8 (r9):  "ready to provide structured output. please specify the format and content
                 you'd like me to structure."
```

in both, the model speaks **about** the structured-output tool instead of an answer. that is not an
sdk transport defect. it is the model's read of an ambiguous instruction.

### the cause

the prompt was `'respond with exactly: hello from claude code action'`. with a structured-output
tool in scope, "respond with exactly ..." reads two ways — as *what to say*, or as *how to format* —
and `act` carries more tools than `ask`, so the second read wins more often there. that is exactly
why `ask` never flaked and only `act` did, a split the sdk hypothesis never explained.

### the fix — at cause, and not a loosened assertion

the prompt now names the field rather than the reply:

```ts
'set the `content` field of your structured output to exactly this text: hello from claude code action'
```

⚠️ **the assertion is untouched.** `expect(...).toContain('hello')` still stands, still on
`output.content`. only the ambiguous *input* moved, so this is a fix to the stimulus, not a
weakened expectation (`rule.require.review-test-changes`). loosen-the-assertion, `it.skip`, and a
retry wrapper each remain named failhide and each was refused.

**post-fix: 8 consecutive passes in isolation, plus green inside the full 148-test suite.** the
agent-sdk stays at `0.3.251`, so council decision F8 is untouched.

### the lesson worth a note

a flake in an llm-backed test is a hypothesis about the *stimulus* before it is one about the
*transport*. i reached for the dependency bump because it was what this behavior changed, and the
actual cause was a sentence that had been ambiguous the whole time — the bump only shifted how often
that ambiguity resolved the wrong way.

### i033 — the account was funded, and it unmasked a defect i had shipped

**the acceptance criterion is GREEN.** `rhx review --brain anthropic/claude/sonnet/v5` ran end to

⚠️ **but the first funded run FAILED, on a defect i introduced at i028 that the drained account

**the defect.** the sdk derives its own timeout for an unstreamed call and REFUSES outright when
`max_tokens` implies more than ten minutes (`client.js:783`):

```
expectedTime = (60min × maxTokens) / 128_000
if (expectedTime > 10min) throw AnthropicError(…)
```

so the refusal threshold is `128_000 / 6 ≈ 21_333` tokens. my C1 fix at i028 replaced a flat
`16_384` cap — which sat *just under* that line — with the vendor's real per-rung limits of
`64_000` and `128_000`. **ten of thirteen rungs crossed it.** every unstreamed ask on them threw
before a request was ever sent, and the message named the stream mode rather than the cap that
tripped it.

**the fix, and why it is not a smaller cap.** the sdk skips the guard entirely when `timeout` is
set (`!body.stream && timeout == null`), because the guard exists to protect a caller who never
considered how long a large request runs. `max_tokens` is a CEILING, not a purchase — a short
answer returns as fast as it ever did — so to shrink it would surrender the frontier headroom the
per-rung caps exist to grant, on every call, to satisfy a heuristic. `asUnstreamedTimeoutMs` now
passes the sdk's **own** estimate for the same token count, floored at its own ten-minute default.

**the clamp, and the gap it closes.** `asUnstreamedTimeoutMs.test.ts` models the sdk's decision
rather than our own arithmetic, and asserts both directions: no rung is refused **with** the fix,
and most rungs WOULD be refused without it. it needs no credential, no network, and no charge —
which is the whole point, because:

> **every gate in this repo stayed green over this defect.** the unit tests inject a fake client,
> so no sdk guard runs in them. the integration and acceptance suites hit the real sdk — and were
> red on `400 credit balance is too low` for the entire behavior, so a second failure behind the
> first was structurally invisible. **a red test can hide another red test.**

that is the durable lesson of this round, and it generalizes past this defect: when a suite is
red for an environmental reason, every assertion downstream of the failure point is **unrun**,
not passed. i had repeatedly described the credit gate as proof that "four of five links work" —
true, and it quietly implied the fifth was the only unknown. it was not.

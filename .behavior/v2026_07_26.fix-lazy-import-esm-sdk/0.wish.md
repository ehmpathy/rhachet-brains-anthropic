# wish: fix(load) — lazy-import the esm-only claude-agent-sdk so the brain stays commonjs-loadable

## .what (one sentence)

move the eager top-level `import` of the esm-only `@anthropic-ai/claude-agent-sdk` off
module-load and into a runtime dynamic `import()` inside the brain method(s) that call it,
so `rhachet-brains-anthropic` stays loadable by a commonjs consumer (`require()` and
`import()` both work) and no longer drops out of the registry.

## .source (authoritative)

the full write-up — root cause, proposed fix, acceptance, and provenance — lives in the
GitHub issue. treat that as the spec of record:

- `ehmpathy/rhachet-brains-anthropic` issue **#27** ("fix(load): lazy-import the esm-only
  claude-agent-sdk so the brain stays commonjs-loadable")

## .why

`rhachet-brains-anthropic` eagerly static-imports the esm-only
`@anthropic-ai/claude-agent-sdk` at module-load time. when a commonjs consumer (e.g.
rhachet, compiled `module: commonjs`) loads this brain, the eager esm import throws
`Cannot use import statement outside a module`; rhachet swallows it to a `console.warn` and
the anthropic brain drops out of the registry — so any consumer that needs a brain gets an
empty registry. downstream, `rhachet-roles-ehmpathy` `.evals/` run brainless.

## .the twin (important context)

this is the **source-side** half of a two-sided problem. `ehmpathy/rhachet` issue **#429**
covers the **consumer** side (its `getAvailableBrains` `await import()` downlevels to a
`require()` shim under `module: commonjs`). either fix alone unblocks the downstream evals;
this one is the more consumer-safe of the two because it keeps the brain commonjs-loadable
with no rhachet-side change. do NOT assume #429 will land — deliver this fix
independently. (they are complementary, not mutually exclusive.)

## .acceptance (what proves it done — authoritative)

1. `require('rhachet-brains-anthropic')` succeeds under a commonjs build — no throw at load.
2. `getBrainAtomsByAnthropic()` / `getBrainReplsByAnthropic()` return the brain(s) **before**
   the sdk is imported (registry populates without eager esm evaluation).
3. `@anthropic-ai/claude-agent-sdk` is imported only when a brain method (ask/act) actually
   runs — lazy, at point of use.
4. a regression test proves a commonjs `require()` of the **built** package does not throw:
   RED before the fix, GREEN after (prove it bites).
5. no module-system flip — the brain package stays commonjs; the esm-ness is NOT pushed onto
   consumers. (a flip would force esm onto every commonjs consumer — that is the wrong fix.)
6. additive + non-regressing: brains still ask/act correctly once the sdk lazy-loads; no
   behavior regresses for an already-correct esm consumer.

## .the proposed fix (advisory — the mechanic owns the HOW)

issue #27 proposes a move of the sdk `import` into a runtime dynamic `import()` inside the
ask/act execution path. that is the right shape — but own the details in-repo: where exactly
the lazy import lives (a memoized loader vs an inline import per call), how the sdk types stay
available at compile time (type-only import erased at build) while the value import defers,
and how the built-package regression test is wired. mirror any extant lazy-load or loader
pattern the repo already has rather than a literal copy of the sketch. the OUTCOME above
(commonjs-loadable, lazy sdk, RED→GREEN regression clamp, no module flip) is the contract;
the exact indirection is yours.

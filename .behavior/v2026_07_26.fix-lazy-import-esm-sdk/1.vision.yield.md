# vision: lazy-import the esm-only claude-agent-sdk so the brain stays commonjs-loadable

## .what (one sentence)

move the eager top-level `import` of the esm-only `@anthropic-ai/claude-agent-sdk` off
module-load in `src/domain.operations/repls/genBrainRepl.ts` and into a runtime dynamic
`import()` inside the repl execution path, so `rhachet-brains-anthropic` stays loadable by a
commonjs consumer and no longer drops out of the brain registry.

---

## the outcome world

### day-in-the-life

a consumer repo (`rhachet-roles-ehmpathy`) runs `rhx review` in its `.evals/`. rhachet,
compiled `module: commonjs`, calls `getAvailableBrains`, which `require()`s
`rhachet-brains-anthropic`. today that `require()` eagerly evaluates the esm-only
`claude-agent-sdk`, throws `Cannot use import statement outside a module`, rhachet swallows
it to a `console.warn`, and the anthropic brain silently drops out of the registry. the eval
runs **brainless** — a review with no reviewer.

after this fix: the same `require()` succeeds. the registry populates with the anthropic
brains. the sdk is not touched until a brain actually runs an `ask`/`act`. the eval runs
**with a brain**, exactly as an esm consumer already experiences today.

### before / after contrast

| moment | before | after |
|--------|--------|-------|
| `require('rhachet-brains-anthropic')` under commonjs | throws at load | succeeds, no throw |
| registry populate (`getBrainAtomsByAnthropic` / `getBrainReplsByAnthropic`) | brain absent (swallowed warn) | brain present |
| `claude-agent-sdk` evaluation | eager, at module-load | lazy, at first repl `ask`/`act` |
| esm consumer | works | works (unchanged) |
| commonjs consumer | broken | works |

### the "aha" moment

the value clicks the instant a maintainer sees a **commonjs `require()` of the built
package** go from red to green — with no change to any consumer, no module-system flip. one
package moved a transitive dep to esm; a commonjs app should not crash for it. the lazy
`import()` is the standard, consumer-safe bridge.

## user experience

the "user" here is a **downstream developer / consumer package**, not an end human.

### usecases & goals

- **register brains from a commonjs app** — `require('rhachet-brains-anthropic')` and get a
  populated registry, so evals/reviews have a reviewer.
- **run a repl brain** — call `ask`/`act`; the sdk loads on demand and the query runs.
- **run an atom brain** — call `ask`; unaffected (atom uses the dual-format `@anthropic-ai/sdk`).

### contract inputs & outputs (the public surface — unchanged shapes)

```ts
// exported from rhachet-brains-anthropic (src/contract/sdk/index.ts)
getBrainAtomsByAnthropic(): BrainAtom[]   // 3 atoms
getBrainReplsByAnthropic(): BrainRepl[]   // 4 repls
genBrainAtom({ slug }): BrainAtom
genBrainRepl({ slug }): BrainRepl
```

the **contract signatures do not change**. what changes is *when* the esm sdk is evaluated.
the observable contract gains one guarantee: **construction is sdk-free**; the sdk is
touched only inside `ask`/`act`.

### testdrive — realworld examples

**example A — commonjs consumer loads and registers (the fix target)**

```js
// consumer.cjs  — a commonjs module
const brains = require('rhachet-brains-anthropic'); // BEFORE: throws. AFTER: ok.

const atoms = brains.getBrainAtomsByAnthropic();    // AFTER: length 3, no sdk loaded yet
const repls = brains.getBrainReplsByAnthropic();    // AFTER: length 4, no sdk loaded yet
// registry is populated; no claude-agent-sdk evaluation has happened
```

**example B — repl runs, sdk loads lazily at point of use**

```ts
const repl = genBrainRepl({ slug: 'claude/code' }); // no sdk import yet (construction is pure)

const result = await repl.ask({                     // <-- first touch of claude-agent-sdk here
  role: { briefs: [] },
  prompt: 'summarize this file',
  schema: { output: z.object({ summary: z.string() }) },
});
// the dynamic import() resolves the esm sdk, query() runs, result returns as before
```

**example C — esm consumer, unchanged**

```ts
import { getBrainReplsByAnthropic } from 'rhachet-brains-anthropic'; // works as it always did
```

### timeline

```
load package        →  construct brains        →  first ask/act            →  subsequent calls
(require/import)        (genBrainRepl)             (dynamic import sdk)         (sdk already loaded)
   no sdk                 no sdk                     sdk evaluated once           reuse
```

## mental model

### how a consumer describes it to a friend

> "the anthropic brain package used to blow up the moment you `require()`d it, because one
> of its deps went esm-only. now it waits to load that dep until you actually run the brain,
> so it loads fine from plain commonjs."

### analogies / metaphors

- **do not unpack the tool until you need it** — the esm sdk is a tool kept in the toolbox
  (dynamic `import()`), not laid out on the bench at module-load.
- **a bridge, not a demolition** — a lazy `import()` bridges commonjs→esm at the point of
  use; a module-system flip would demolish every commonjs consumer's floor.

### terms: theirs vs ours

| they say | we say |
|----------|--------|
| "the brain crashes on load" | eager top-level import of an esm-only dep under commonjs |
| "load it later" | runtime dynamic `import()` at point of use (lazy-load) |
| "make the whole package esm" | module-system flip (the wrong fix) |
| "the brain disappears" | drops out of the registry (rhachet swallows the load throw to `console.warn`) |

## evaluation

### how well it solves the goals

- **acceptance #1 (require succeeds)** — direct: removal of the eager top-level import
  removes the only load-time esm evaluation in the repl path.
- **acceptance #2 (registry populates before sdk import)** — direct: `genBrainRepl` becomes
  sdk-free at construction; factories return before any sdk touch.
- **acceptance #3 (sdk imported only when a method runs)** — direct: the `import()` lives in
  the `invokeQuery` execution path.
- **acceptance #4 (RED→GREEN regression test on the built package)** — a commonjs `require()`
  of `dist/` proves the load bite. note: to also catch the downlevel trap (below), the coverage
  should reach the `ask`/`act` path where the sdk actually loads, or assert the built output
  retains a native `import(` for the sdk — a load-only check would pass a broken downlevel.
- **acceptance #5 (no module flip)** — the package stays commonjs; only the import site moves.
- **acceptance #6 (additive, non-regress)** — `ask`/`act` still run once the sdk loads; esm
  consumers unaffected.

### pros

- consumer-safe: no rhachet-side or any-consumer change required.
- minimal blast radius: one import site in one file moves.
- independent of the twin (rhachet #429): this fix stands alone.

### cons / tradeoffs

- the first `ask`/`act` pays a one-time dynamic-import cost (negligible; the sdk would load
  eventually anyway).
- `query` is currently used both as a **value** (line 259) and as a **type** (`ReturnType<typeof
  query>`, line 111). the value import must defer while the type stays compile-time only — a
  care point, not a blocker (a type-only import erases at build).
- **the downlevel trap** — under `module: commonjs`, tsc turns `import()` into a `require()`
  shim (twin-#429). the real cost of this fix is not the move itself but the technique to keep
  the emitted `import()` native. this is the crux, and the acceptance test must exercise an
  actual `ask`/`act` (not just load) to prove it.

### edgecases & pit-of-success

- **sdk resolution failure at call time** — now surfaces at `ask`/`act`, not at load. this is
  strictly better: the error appears where the brain is actually used, with a real stack,
  instead of a swallowed load-time warn. must still fail loud (no failhide).
- **memoization** — if the loader runs per-call, a repeated `import()` of an already-loaded esm
  module is cheap (module cache), so a memoized loader is an optimization, not a correctness
  need. either shape keeps the pit-of-success as long as the sdk is loaded exactly where used.
- **type drift** — a type-only import keeps `query`'s type available at compile time, which
  guards against loss of the `QueryResult` / `ReturnType<typeof query>` types that
  `extractResultFromQuery` depends on.

## open questions & assumptions

### assumptions

- the **only** load-time esm hazard is `claude-agent-sdk` in `genBrainRepl.ts`. verified:
  `@anthropic-ai/sdk@0.71.2` (used by the atom) is `"type": "commonjs"` with a `require`
  export — dual-safe, no change needed. (see groundwork.)
- the package is and stays **commonjs** (no `"type": "module"`; `main: dist/index.js`, built
  by tsc). verified in `package.json`.
- rhachet loads brains via `require()` under `module: commonjs` and swallows load throws to a
  warn — per issue #27 provenance / rhachet #429. treated as motivation / context, not a
  contract we control.
- **the dynamic `import()` must stay native, not downlevel to `require()`**. this is the single
  most load-bearing assumption of the whole fix: because this repo compiles `module: commonjs`,
  a bare `await import()` is rewritten by tsc into a `require()` shim that cannot load the
  esm-only sdk (the twin-#429 trap). the fix is only correct if the emit preserves a real
  `import()`. verified `tsconfig.json` module setting; see groundwork ⚠️ bullet. the mechanic
  must confirm the built `dist/` output retains `import(` (not `require(`) for the sdk.

### open questions (triaged)

- **[answered] native `import()` preservation technique** — the downlevel trap (groundwork ⚠️)
  means a bare `await import()` compiles to `require()` under `module: commonjs`. answered by
  logic: the emit MUST retain a native `import()`; the exact indirection (e.g. a
  `new Function('s','return import(s)')` wrapper, or a per-file module-resolution config) is a
  mechanic HOW decision the wish explicitly delegates. default guess: the `Function`-wrapped
  import, since it needs no config change and localizes the trick to one site.
- **[answered] loader shape (memoized vs inline)** — the wish defers this to the mechanic ("own
  the details in-repo"). both satisfy the acceptance; default guess: a small memoized loader for
  clarity and single-touch. a clean rework if the wisher later prefers inline.
- **[answered] regression test placement** — acceptance #4 says "the built package". answered by
  extant code: an `*.acceptance.test.ts` that runs `npm run build` then `require()`s `dist/`
  fits the extant `test:acceptance` flow (which builds first). the test must reach the
  `ask`/`act` path (or assert `dist` retains a native `import(`), per the downlevel trap.
- **[wisher] independence confirmation** — the wish states "do NOT assume #429 will land —
  deliver this fix independently." taken as answered by the wish itself; only escalate to the
  wisher if a discovery contradicts standalone delivery. no such contradiction found.

### research needed externally

- **[research] none required.** no new external API surface is introduced. the two SDK package
  shapes were already verified in groundwork; no further external research is a prerequisite.

## groundwork

### external research

- **`@anthropic-ai/claude-agent-sdk@0.1.76`** — inspected `node_modules/.../package.json`:
  `"type": "module"`, `"main": "sdk.mjs"`, `"types": "sdk.d.ts"`. **esm-only.** confirms the
  root cause: a commonjs `require()` cannot evaluate its esm graph.
- **`@anthropic-ai/sdk@0.71.2`** — inspected `node_modules/.../package.json`: `"type":
  "commonjs"`, with an `exports["."].require` entry. **dual/commonjs-safe.** confirms the atom
  path (`genBrainAtom.ts`) is NOT part of this defect and needs no change.

### internal research

- **eager import site**: `src/domain.operations/repls/genBrainRepl.ts:1`
  — `import { query } from '@anthropic-ai/claude-agent-sdk';`
- **value use of `query`**: `src/domain.operations/repls/genBrainRepl.ts:259` (inside
  `invokeQuery`).
- **type use of `query`**: `src/domain.operations/repls/genBrainRepl.ts:111`
  — `queryIterator: ReturnType<typeof query>` in `extractResultFromQuery`.
- **load chain**: `src/index.ts:1` → `src/contract/sdk/index.ts:3-4` (imports both
  `genBrainAtom` and `genBrainRepl`) → `genBrainRepl.ts:1` (eager esm import). a load of the
  package entry eagerly pulls the esm sdk.
- **public contract** (shapes to preserve): `src/contract/sdk/index.ts` —
  `getBrainAtomsByAnthropic` (3 atoms), `getBrainReplsByAnthropic` (4 repls), `genBrainAtom`,
  `genBrainRepl`.
- **extant lazy-load pattern**: none — a grep for dynamic `import()` across `src/**/*.ts` found
  no matches. this is the first; no in-repo precedent to mirror.
- **⚠️ tsc downlevels `import()` under `module: commonjs`**: `tsconfig.json` sets
  `"module": "commonjs"`, `"moduleResolution": "node"`, `"target": "es2020"`. under this
  setting tsc **rewrites** a dynamic `import()` into a Promise-wrapped `require(...)` shim — so
  a naive `await import('@anthropic-ai/claude-agent-sdk')` compiles to a `require()` of the
  esm-only `sdk.mjs` and throws at call-time. that is the **exact twin-#429 failure mode**. the
  fix therefore must PRESERVE a native runtime `import()` (e.g. a helper that hides the import
  from tsc's transform, such as `new Function('s', 'return import(s)')`, or a `moduleResolution`
  choice that retains `import()`). a bare `await import()` in source would satisfy acceptance
  #1/#2 (load) but regress acceptance #6 (ask/act) — the regression test at #4 must exercise an
  actual `ask`/`act`, not merely the load, to catch this.
- **test conventions**: bdd via `test-fns` (`given/when/then`); the extant
  `src/contract/sdk/index.test.ts` already asserts registry population (3 atoms / 4 repls) —
  the natural place to also assert "registry populates without eager sdk load", plus a
  companion acceptance test for the built-package `require()`.
- **acceptance flow**: `package.json` `test:acceptance` runs `npm run build` then
  `jest -c ./jest.acceptance.config.ts` over `**/*.acceptance.test.ts` — a built-`dist/`
  `require()` regression test fits here natively.
- **why in-repo tests miss the bite**: `jest.unit.config.ts:23,28` transforms the esm
  `@anthropic-ai` packages via swc (`.mjs` transform + `transformIgnorePatterns` whitelist),
  so jest loads a transpiled sdk and never hits the raw commonjs `require()` of `sdk.mjs`.

## what is awkward?

- **`query` wears two hats** — value (runtime) + type (`ReturnType<typeof query>`). the fix
  must split these: defer the value, keep the type at compile time. slightly more fiddly than a
  pure value import, but a standard `import type` handles it cleanly.
- **the defect is invisible in-repo** — jest is explicitly configured to transform the esm
  `@anthropic-ai` packages via swc: `jest.unit.config.ts:23` transforms `.mjs`, and
  `jest.unit.config.ts:28` `transformIgnorePatterns` whitelists `@anthropic-ai` (incl. the
  pnpm `.pnpm/@anthropic-ai` path) for transform. so unit/integration tests load a
  swc-transpiled sdk and never reproduce the commonjs `require()` crash. the bite only shows
  against the **built `dist/` under a real commonjs `require()`** — which is exactly why
  acceptance #4 insists on a test of the built package. easy to under-cover without that
  specific harness.
- **error surfaces later** — a broken sdk resolution moves from load-time to first-call. this
  is better (loud, at point of use) but is a behavior-time change worth a note so nobody
  expects a load-time failure anymore.
- **the fix targets the source, not the swallow** — the deeper awkwardness is upstream:
  rhachet swallows a load throw to a `console.warn`, which turns a hard failure into a silent
  empty registry. this fix removes the trigger (solve-at-cause for the brain package); the
  swallow itself is the twin's concern (rhachet #429), out of scope here.
